# 第一阶段本地验收步骤

全程先运行MongoDB和项目服务器。所有数据都是本地课程测试数据，页面上不要填写真实敏感资料。

## 五分钟演示

1. 进入 `http://127.0.0.1:8000`，注册自己的账号A并登录。
2. 点击“体验四题型示例”，可见单选、数字、多选、文本四题，规则和约束均可编辑。
3. 点击“规则自动体检”，预期绿色“体检通过”。点击发布，确认冻结，得到 `/survey/{id}` 链接。
4. 打开分享链接并开始填写：第1题选“从不使用”，预期自动到第3题；选“开放时间”，预期直接核对并结束，路径为 `q1 → q3 → 结束`。匿名提交。
5. 返回问卷再填一次：第1题选“经常使用”，第2题输入8.5，预期提示“必须是整数”；改成8，预期跳到第4题；输入至少2字的建议，提交。路径为 `q1 → q2 → q4`。
6. 返回工作台，点击查看统计：总提交数2；单选“经常使用”1、“从不使用”1；数字题回答1人、均值8；多选“开放时间”1；文本内容可见。查看提交记录，两份身份均为匿名。
7. 点击关闭问卷，再次进入链接，预期显示已关闭；已有统计保留。

以上步骤已用浏览器真实执行到第6步，留有 `docs/screenshots` 截图。第7步及更多状态边界已由真实MongoDB集成测试验证。当前演示问卷仍保留已发布状态，便于继续查看。

## 创新点现场展示

- 规则体检：新建示例草稿，把数字最小值设为30、最大值设为2，体检会报错，不能发布。
- 规则目标稳定：修改题序时沿用题目ID；若形成回跳，发布体检指出目标错误。
- 服务端重算：API提交跳过题答案会422，不能靠浏览器伪造答案影响统计；见自动测试 `test_invalid_submission_rejected`。
- 可解释路径：提交核对页显示访问题号，作者回答API保存trace，可解释哪条规则造成跳转。
- 并发去重：自动测试同时发送6次单次填写请求，只保存1份；同幂等键并发重试返回同一个回答ID。
- 第一阶段快照：运行 `python scripts/verify_snapshot.py`，可核对源码与设计未被第二阶段改写。

## 多账号与权限验收

使用另一个浏览器配置文件或无痕窗口注册账号B（同一地址）。B的“我的问卷”不显示A的问卷；B可登录后填写A发布的链接，但访问A的管理、stats、responses接口返回404。匿名选项关闭时，提交界面不再提供匿名勾选。

默认新问卷不允许同账号多次填写；再次提交返回409。示例问卷特意允许多次，便于演示不同路径。通过设置 `min_choices=max_choices=2` 演示精确选择2项。

## 截止时间验收

新建草稿，把截止时间设置到未来1分钟。发布并等待超过该时间，再打开分享链接，显示不能填写；即使先打开网页后等待到期，下一题与提交API也会拒绝。输入时使用本机时间；后端存储带时区日期，API必须提供时区。数据库状态无需被定时任务改成closed，accepting=false即生效。

## 退出与重启

点击退出后作者列表和填写API都要求重新登录。停止并重启服务器后，已发布问卷、回答和未过期会话仍在MongoDB，不依赖内存。若要换端口，分享链接必须同步使用新端口。

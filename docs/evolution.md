# 第二阶段未来演化设计

本文仅给出增量演化方案，不代表第一阶段已实现这些能力。第一阶段核心仍为四集合与问卷内嵌题目。题库、共享、题目历史版本、恢复版本、反向引用和跨问卷题目统计没有接口、页面或数据集合实现。

## 第一阶段基线

surveys.questions 是问卷自己的题目副本；发布后冻结。responses 以 survey_id、survey_revision、answers中的本地题号关联该副本。这有利于第一阶段一次加载、路径计算和历史稳定，但同一题重复创建会冗余，也无法识别不同问卷中语义相同的题。

已通过 snapshots/stage1_baseline.zip 与SHA-256清单保留源码、设计、测试和报告。第二阶段从当前代码扩展，不能重写后替换第一阶段。

## 变更需求与增量方案

| 新需求 | 原结构局限 | 第二阶段拟扩展 |
|---|---|---|
| 常用题保存、重复使用 | 题目只属于一个问卷 | 新增 question_versions，保存不可变题目版本；新增逻辑题根标识question_root_id |
| 共享给其他用户 | 无题目级授权 | 新增question_shares，标记可使用者，创建问卷时检查授权 |
| 改题不影响已发布问卷 | 第一阶段通过整卷冻结保证 | 保留嵌入快照；选题时附source_question_version_id，题库修改生成新版本 |
| 历史、来源与恢复 | revision只表示草稿编辑次数 | parent_version_id形成版本链/分支；恢复旧版是基于旧版创建新版本，不覆盖旧文档 |
| 不同版本共存 | 没有跨卷版本身份 | 每个版本独立不可变文档，不同问卷指向不同版本并保留自己的快照 |
| 查看被哪些问卷使用 | 无题目来源关系 | 在surveys.questions.source_question_version_id建立多键索引反查；必要时新增usage集合并保证一致性 |
| 题库管理 | 无组织容器 | 新增question_banks，保存拥有者/协作者与条目引用，不把所有历史塞进一份无界文档 |
| 跨问卷单题统计 | q1在不同问卷中不代表同一道题 | 通过版本引用建立可追溯映射；先按确切版本统计，再由作者显式决定是否合并兼容版本 |

## 保留核心结构

继续保留 users、sessions、surveys、responses、作者权限边界、状态机、规则引擎和答案校验器。问卷编辑器仍输出同一 Question 结构，新增可选来源元数据。规则继续引用问卷本地题号，不能直接引用跨问卷题库ID，否则重复选同题或重排时可能产生歧义。

已发布问卷的内嵌快照仍是答题和历史统计的权威定义；共享者修改题目不会改变旧问卷。responses已有 survey_revision 可继续使用；必要时新回答附带本地题号到版本ID的映射，避免后续查错版本。

## 迁移步骤设想

1. 校验第一阶段快照，备份真实MongoDB，不修改原归档。
2. 引入schema_version=2，并提供兼容读取路径：无来源字段的旧内嵌题继续正常工作。
3. 新增题目版本集合和题库/授权接口；采用适配层把题库题转成第一阶段Question形状，复用规则体检与提交逻辑。
4. 旧题目可按需提升为题库初版，保留来源问卷与本地题号映射；不可仅靠标题相同就自动合并，避免错误合并语义。
5. 对跨问卷统计建立显式版本选择策略。选项删改或数字单位变动会使不同版本不可直接合并，应提示分版本统计。
6. 增加授权、版本不可变、分支/恢复、反向引用、迁移幂等与跨卷统计测试，同时重跑全部第一阶段测试。

## 尚待第二阶段决定的取舍

版本链与共享范围的具体权限模型、题目删除策略、跨版本合并准则、历史数据迁移脚本与回滚策略，需要在第二阶段正式实现时确定并测试。第一阶段不提前创建空题库集合、不展示未实现按钮、不把设计方案计入已完成功能。
